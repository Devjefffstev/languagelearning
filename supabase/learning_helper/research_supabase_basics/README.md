# Supabase Basics: Deploy a Simple Database with Python

## Description

Supabase is an open-source "backend as a service" built on top of PostgreSQL — the world's most popular open-source relational database. Instead of installing and babysitting a database server yourself, Supabase hosts one for you in the cloud. You already have two Supabase projects, and each project *is* its own isolated Postgres database plus a set of tools around it.

"Deploying a database" with Supabase is two steps, and you've already done the first one: the platform provisions the Postgres server (that's your project). The second step is defining your schema by running SQL like `create table ...` in the dashboard's SQL Editor. The moment you click Run, your database exists and is reachable over the internet.

The feature that makes Supabase feel magical for beginners: every table you create instantly gets a REST API (an HTTP interface, generated by a tool called PostgREST). You write zero server code. From Python, the `supabase` package talks to that API using just two values from your project settings: the Project URL and an API key.

In this guide you'll create a small vocabulary database (words + translations — fitting, since this lives in a language-learning repo), insert and query data from Python, and practice with four exercises that build up to a small command-line tracker.

## Analogy

Think of Supabase as a **restaurant**.

- The **Postgres database** is the kitchen: all the ingredients (your data) live there, and SQL is the cooking technique.
- The **auto-generated REST API** is the wait staff: you place an order in a standard format (HTTP) against any table, in any programming language, and food (JSON data) comes back. You never need to enter the kitchen yourself.
- The **SQL Editor** in the dashboard is the chef's prep station: it's where you define the menu (create tables and rules) before any customer arrives.
- **Grants and Row Level Security (RLS) policies** are the house rules: grants decide which operations a guest may attempt at all; policies decide which dishes (rows) each guest may actually get.
- Your **Python script** is simply a customer: it shows a name tag (the API key) and places orders.

Mapping back to reality: running `setup_quick.sql` in the SQL Editor sets up the kitchen's storage and house rules; each `supabase.table(...)` call in Python is an order; the response `.data` is the dish that comes back.

## Examples

### Example #1 — Quick setup (hello, database)

#### Quick setup

Goal: create a `words` table and insert + read rows from Python in about five minutes.

1. Open your Supabase dashboard (use either of your two projects as a sandbox) → **SQL Editor** → **New query**.
2. Paste the contents of `examples/setup_quick.sql` and click **Run**. You just deployed a table.
3. Get your credentials: click **Connect** at the top of your project's dashboard (or open **Project Settings → API Keys**) and copy the **Project URL** and the **publishable key** (it starts with `sb_publishable_`). If your project still shows the legacy **`anon` / "anon public"** key (a long `eyJ...` JWT), that works too — it does the same job for these scripts.
4. In your terminal — **run one line at a time**, not as a paste:

```bash
cd learning_helper/research_supabase_basics
python3 -m venv .venv          # one-time: create a private Python sandbox for this guide
cp .env.example .env           # then open .env and paste your Project URL + publishable key
.venv/bin/python3 -m pip install supabase python-dotenv
.venv/bin/python3 examples/quick_setup.py
```

**Why a virtual environment?** On macOS, Homebrew's Python refuses system-wide `pip install` (the `externally-managed-environment` error). A `.venv` gives this project its own private Python with its own packages, and it's git-ignored. Calling `.venv/bin/python3` directly — as in the block above — needs no activation at all. In an interactive terminal you can alternatively `source .venv/bin/activate` once and then use plain `python3` and `pip`.

The `.env` file keeps your credentials in one place — no `export` commands, nothing in your shell history. Every script in this guide loads it with `load_dotenv()`, and the `.gitignore` in this folder keeps both `.env` and `.venv/` out of git. Use a **publishable** key (`sb_publishable_...`) — or the legacy `anon` key, which still works but is being retired by the end of 2026. Never use the **secret** key (`sb_secret_...`, or legacy `service_role`): it bypasses every Row Level Security policy and belongs on servers only.

5. The heart of the script is just this:

```python
import os

from dotenv import load_dotenv
from supabase import create_client

load_dotenv()  # reads SUPABASE_URL / SUPABASE_KEY from the .env file
supabase = create_client(os.environ["SUPABASE_URL"], os.environ["SUPABASE_KEY"])

# Write: insert two rows in one call
result = supabase.table("words").insert([
    {"word": "hola", "translation": "hello", "language": "spanish"},
    {"word": "gracias", "translation": "thank you", "language": "spanish"},
]).execute()

# Read: fetch every row
rows = supabase.table("words").select("*").execute().data
for row in rows:
    print(row["word"], "=", row["translation"])
```

#### Complete setup

Goal: a realistic tour — upsert, filtered selects, update, delete, exact counts, and calling a custom Postgres function from Python.

1. Run `examples/setup_complete.sql` in the SQL Editor. It rebuilds `words` with a richer schema, adds full-CRUD permissions, and creates a `word_stats()` function.
2. With your `.env` in place, run:

```bash
.venv/bin/python3 examples/complete_setup.py
```

3. The script demonstrates, with a comment on every block: seeding with `upsert` (safe to re-run, no duplicates), filtered + ordered + limited selects, `update` and `delete` always paired with an `.eq(...)` filter, exact row counts with `count="exact"`, and `supabase.rpc("word_stats")` — a Postgres function doing the aggregation inside the database while Python just receives the result. Read the file top to bottom; it doubles as a cheat sheet.

- https://postgrest.org/en/stable/ — documentation for PostgREST, the engine that turns your Postgres tables into the REST API your Python code calls.

## Next steps

Once the exercises feel comfortable, go deeper in three directions. First, read the Row Level Security guide above properly and replace the wide-open sandbox policies with per-user policies tied to Supabase Auth — that's the single most important step from "learning project" to "real app". Second, install the Supabase CLI and try `supabase init` plus migrations, so your schema lives in files in this repo instead of only in the dashboard. Third, build something small and real on top of what you made here — a FastAPI or Flask endpoint that quizzes you on unlearned words is a perfect next project.
